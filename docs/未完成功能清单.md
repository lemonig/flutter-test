### A1. M0-07 地图选点与逆地理编码

**现状**：签到、巡检都用系统定位（geolocator）拿坐标，再按距离列出附近站点，**没有地图界面**。地址靠站点自带 `address` 字段，不是实时逆地理。

**卡在**：高德两个 Key 都不可用。**2026-11-05 已实测确认**，不是推测。

| Key | 平台 | 实测结果 |
|---|---|---|
| `989f15a5d1efca77bd42d7a0dfaad11b` | Web 服务 | 逆地理 / POI / 关键字三个接口全部 `10007 INVALID_USER_SIGNATURE` —— 该 Key 开了「数字签名」，缺安全密钥 |
| ~~`f6457d0b866d0dc5e93e7f95f4a9bdc5`~~ → `8d3f5d8cfd5aaeca927a4b99dd244011` | Android 地图 SDK | ✅ 已解决（2026-11-06）：新 Key 绑 `com.greandata.green_clean_ops` + debug SHA1，模拟器实测瓦片渲染正常。Release 包需再绑定 release keystore 的 SHA1 |

**解锁条件**（任一组合）：
1. 控制台拿到 Web 服务 Key 的**安全密钥**，或关掉数字签名；
2. 为 `com.greandata.green_clean_ops` + 签名 SHA1（debug / release 各一个）申请或改绑地图 Key。

**落地要点**：
- 地图渲染 → `amap_flutter_map`（需同时配 Android 与 iOS Key）；只需要选点的话，也可以先用 `amap_flutter_location` 定位 + 列表选点，绕开地图。
- 逆地理 / POI 搜索 → 直接 HTTP 调 `restapi.amap.com/v3/geocode/regeo`、`/v3/place/around`（详见 B2）。
- 涉及页面：`create_attend_page.dart`（签到站点匹配）、`submit_inspection_page.dart`（站房校验前的位置确认）、M9-03 地址管理。

**地图渲染的地基已经打好**（2026-11-05）：

- `android/.../amap/AmapPlatformView.kt`：直接承载原生 `MapView`（官方 `amap_flutter_map` 3.0.0 是 AGP 3.5 写法，编不过，已弃用）

- `lib/core/amap/amap_view.dart`：Dart 侧 `AndroidView` 挂载 + 取中心点 / 移动相机 / 点击回调
- `lib/core/amap/map_picker_page.dart`：地图选点页（准星 + 实时坐标 + 使用此位置），已接进「我的 → 地址管理」

**真机实测**：页面完全正常（定位自动取到坐标、准星居中、按钮可点），只是底图瓦片为空白 —— 与 logcat 的 Key 校验失败吻合。**改绑 Key 后不需要改任何代码**，地图就出来了。

**当前替代方案**（已上线）：定位 + 20 公里内站点列表按距离排序，偏差以「距当前位置 x 米」表达，够用但不如图上选点直观。

### A2. M6-04 厂商通道（离线推送）

**现状**：只接了个推**在线通道**。App 进程被杀后，通知收不到 —— 移动端最常见的投诉就是这个。

**卡在**：需要在各厂商开发者后台申请推送服务，拿到各家的 AppID / AppKey / AppSecret：

| 厂商 | 需要的东西 |
|---|---|
| 小米 | AppID + AppKey |
| 华为 | AppID（需 HMS Core） |
| OPPO | AppKey + AppSecret + MasterSecret |
| vivo | AppID + AppKey + AppServerKey |
| 魅族 | AppID + AppKey |

**解锁条件**：各家后台申请通过（通常需要企业资质 + 应用包名/签名，各 1–3 工作日）。

**落地要点**：
- 写进 `android/app/build.gradle.kts` 的 `manifestPlaceholders`，字段名与插件期一致：
  `XIAOMI_APP_ID` / `XIAOMI_APP_KEY` / `HUAWEI_APP_ID` / `OPPO_APP_KEY` / `OPPO_APP_SECRET` / `VIVO_APP_ID` / `VIVO_APP_KEY` / `MEIZU_APP_ID` / `MEIZU_APP_KEY`。
- 厂商 SDK 由 `gtsdk` 通过 `com.getui:gtc` 的 assist 组件反射加载，**只要配置齐全，客户端代码不用改**。
- 验证：`adb shell am force-stop` 杀掉进程后再推，看通知栏是否到达。

### A3. M10-05 Android 正式发布

**现状**：只有 debug 包（228 MB，带 VM Service），`dist/` 里三个 flavor 都是 debug。release 构建能跑，但用的是 debug 签名。

**卡在**：
- 正式签名证书（`.jks`）+ 密码；
- 应用市场开发者账号（华为 / 小米 / OPPO / vivo / 应用宝，各需企业资质）。

**落地要点**：
1. `android/app/build.gradle.kts` 加 `signingConfigs`，从 `key.properties` 读密码（**不要提交到仓库**）；
2. `tool/build_apk.ps1` 里把 `--debug` 改成参数化（目前硬编码 `'build','apk','--debug'`）；
3. 开 `minifyEnabled = true` + `shrinkResources`，配 `proguard-rules.pro`；个推 SDK 需要 keep 规则，否则收不到推送；
4. 隐私清单：`AndroidManifest` 里声明收集的信息类型（定位、相册、设备标识），市场审核会逐项对照隐私政策；
5. 预期包体：debug 228 MB → release 约 25–35 MB。

## B. 需后端配合

### B1. 推送点击跳转任务详情（M6-04 补充）

**现状**：点通知只是打开 App 首页。服务端 `AppPushService` 里 `notification.clickType = "startapp"`，**没有携带任何 payload**。

**需要后端**：在 `pushDTO` 的 `pushMessage.notification`（或 `ups.notification`）里加 `payload`，内容建议：

```json
{"route": "task", "id": 68098}
// 或 {"route": "inspection", "id": 12495900} / {"route": "attend", "id": 54981}
```

**落地要点**：
- 原生 `GreenIntentService.onNotificationMessageClicked(context, message)` 里读 `message.payload`（当前是空实现）；
- 冷启动时需要把 payload 暂存，等 Flutter 引擎起来后再通过 MethodChannel 推给 Dart（`PushBridge` 已有 `pendingClientId` 的先例，照抄一份 `pendingPayload`）；
- Dart 侧拿到后 `router.go(detailPathFor(category, id))`，注意此时可能还没登录，要排队等鉴权完成。

### B2. 地址能力走后端代理（M0-07 / M9-03 前置）

**现状**：`ops-mobile` **没有高德 REST 代理**。`model/amap/{AMapAddress,AMapGeoCode,AMapOrg}.java` 是 2019 年的遗留类，全项目无人调用。

**为什么需要代理**：高德 Web 服务 Key 若开数字签名，私钥（安全密钥）必须参与 `sig` 计算；把私钥打进 APK 等于公开，反编译即可白嫖配额。

**需要后端**：
- `POST /api/meta/regeo {coordinate1, coordinate2}` → 返回 `{address, adcode, city, district}`
- `POST /api/meta/poi {coordinate1, coordinate2, keyword, radius}` → 返回 POI 列表（用于地址管理选点）

**落地要点**：后端用 `RestTemplate` 调 `restapi.amap.com/v3/geocode/regeo`，Key 与安全密钥放 `application.properties`（`amap.key` / `amap.securityCode`）。客户端两个接口一接，M9-03 就能落地。

**备选（不推荐）**：客户端直连 + 私钥硬编码，仅适合内网自用。

### B3. 消息「全部已读」批量接口（M6-03 补充）

**现状**：后端 `readMessage` 只按 `message_type` 更新，没有跨分类接口。客户端实现为「对有未读的分类逐个 `message/type {limit:1}`」，最多 7 次请求。

**需要后端**：`POST /api/message/read_all`（一条 `UPDATE ... WHERE user_id=? AND is_read=0`）。

**影响**：不阻塞功能，只是浪费几个请求、略微慢。用户点「全部已读」时先本地清零已给即时反馈。

## D. 已知取舍（不是遗漏）

这些是**主动做的决定**，列出来避免以后被当成 bug 修。

| 编号 | 取舍 | 原因 |
|---|---|---|
| D1 | 消息是「推送流水」，不是聊天 | 后端 `MessageController` 没有会话与发送接口，原规划的「聊天详情 / 发图 / 发送重试」不存在 |
| D2 | 巡检项没有「正常 / 异常 / 不适用」三态 | `ops_record_detail` 表只有 `pictures` + `description`，完成度由「有无备注或照片」推导 |
| D3 | 签到照片走后端代传（`upload/6/file`），不是 OSS STS 直传 | 两者产物同为 `check/` 前缀 key，落库与展示链路一致；STS 直传需额外做签名 PUT，收益低 |
