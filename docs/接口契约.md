# 后端接口契约（以 ops-mobile 源码为准）

> **权威来源**：`F:\yunwei\ops-mobile`（Spring Boot 2.1.1 / MyBatis / Redis / MySQL，341 个 Java 文件）
> **交叉验证**：`F:\yunwei\yunwei-ios2` 的 `NetworkTool.swift` 与各业务调用点
> **实测环境**：`http://192.168.188.66:1601/api/`（2026-11-04 已验证可达）
> 本文描述的是后端真实实现，与 iOS 侧反推结论有出入的地方以本文为准。

## 1. 环境

| 环境 | baseUrl | 来源 |
|---|---|---|
| 本机联调 | `http://192.168.188.66:1601/api/` | 用户启动的 UAT 实例（`application-uat.properties` 默认 1601） |
| 开发 | `http://47.111.166.172:1600/api/` | `application-dev.properties` |
| 正式 | `https://app.greandata1.com/api/` | iOS `ProjectTool.currentReleaseBaseUrl` |

- 所有 Controller 都标注 `@RequestMapping("/api")`，因此 baseUrl **必须带 `/api/`**。
- 当前 `spring.profiles.active=uat`；UAT 连阿里云 RDS `other_linghu` 库、Redis 本机 12 库。
- dev/UAT 是 HTTP 明文，Android main 清单已开 `usesCleartextTraffic`；生产必须 HTTPS。
- 后端启用了 Swagger 2.9.2：`/v2/api-docs`、`/swagger-ui.html`。

## 2. 鉴权

- 请求头 **`token: <uuid>`**（`RedisUtilService.getUserId` 读 `request.getHeader("token")`）。
- 登录后 token 写在 Redis `user:token:%s`；`logout` 清 token。
- 未认证或过期时抛 `ServerException(UNAUTHENTICATED, "用户未认证或token过期，请重新登录后继续")`，**HTTP 状态仍是 200**，靠响应体 `success=false` 判断。
- `meta/auth` 返回的 `SimpleUser` **不含 token**（`fromUser(user)` 未 setToken），Flutter 侧需回填本地旧 token。

## 3. 统一响应体

成功（`com.grean.ops.model.meta.ApiResponse`）：

```jsonc
{
  "success": true,
  "data": { } | [ ],
  "additional_data": { "total": 37, "totalPage": 4, "startPage": 1,
                       "limit": 10, "more_items_in_collection": true },
  "related_objects": { },
  "request_time": "2026-11-04T22:15:37.707+08:00"
}
```

失败（`ApiErrorResponse extends ApiResponse`，实测样本）：

```jsonc
{
  "success": false,
  "message": "账户或密码不能为空",   // 面向用户的原文
  "error": "FIELD_ERROR",            // 错误码
  "path": "/api/login",
  "request_time": "..."
}
```

错误码枚举 `ErrorCode`：`API_ERROR` / `FIELD_ERROR` / `NOTFOUND_OR_UNAUTHORIZED` / **`UNAUTHENTICATED`** / `PAGE404` / `AliyunOssError`。

> ⚠️ 与 iOS 侧反推的差异：iOS `NetworkTool` 只读 `success` 与 `error`，实际后端成功时没有 `error` 字段、失败时才由 `ApiErrorResponse` 补上。Flutter 侧 `ApiResponse.failure` 已兼容 `error ?? message`。

## 5. 首页三类时间线

三个 Controller 形态一致，均为 `POST`，`data` 为数组，`additional_data` 为 `PaginationVO`。

| 分类 | 接口 | 请求 Form | condition 个数 |
|---|---|---|---|
| 异常 | `/task/timeline` | `TaskQueryForm` | 4 |
| 巡检 | `/opsrecord/timeline` | `OpsQueryForm` | 3 |
| 签到 | `/attend/timeline` | `AttendQueryForm` | 2 |

`Pagination`：`startPage`（从 1 开始）、`limit`（默认 20，最大 1000）。服务端 `init()` 会算 `start=(startPage-1)*limit`。

### ⚠️ condition 是数字编码，不是中文文案

后端 `AppService.translateXxxQueryForm` 把字符串编码翻译成业务字段。**这是与 iOS 反推契约最大的差异**，Flutter 侧已在 `TaskFilterConfig` 做 label→code 映射。

**异常（顺序固定）**

| 参数 | 分组 | 编码 |
|---|---|---|
| condition1 | 可见范围 | 1 全部 / 2 我处理的 / 3 我发出的 / 4 我转交的 / 5 未读 |
| condition2 | 任务状态 | 1 全部 / 2 待处理 / 3 处理中 / 4 已提交-非异常 / 5 已提交-已修复 / 6 已关闭 / 7 已终止 / 8 超时 |
| condition3 | 其他 | 1 全部 / 2 产品缺陷导致 |
| condition4 | 所属省份 | 1 全部 / 其它为 org regionKey（动态） |

**巡检**：condition1 可见范围（1 全部 / 2 我处理的 / 3 我转交的 / 4 未读）；condition2 任务状态（1 全部 / 2 未完成 / 3 已完成 / 4 已过期 / 5 已终止）；condition3 省份。

**签到**：condition1 可见范围（1 全部 / 2 我的签到）；condition2 省份。

> `null` 与 `"1"` 等价（后端会回落），Flutter 侧统一显式传 `"1"`。省份列表由 `orgService.getRegionList()` 动态生成，必须从 `meta/basic` 拉取。

### 列表 VO 字段

- `TaskListItemVO`：`id`、`station{name,regionTitle,cityTitle}`、`state`（`TaskStateEnum` 1~7）、`content`、`executor{nickname,avatar}`、`pictures:[PictureBO{picture,url,title}]`、`gmt_create`、`jobNumber`、`overtime`、`deadline`、`countRead/countLike/countComment`
- `OpsRecordListItemVO`：`id`、`station`、`executor`、`description`、`pictures:[String]`、`opsTaskDone`、`terminated`、`overtime`、`gmt_create`、`gmt_first_submit`、`itemSize`、三个 count
- `AttendVO`：`id`、`user{nickname,avatar}`、`station`、`address`、`description`、`pictures:[PictureBO]`、`coordinate1/2`、`gmt_create`、`jobNumber`

`TaskStateEnum`：1 待处理 / 2 处理中 / 3 已修复 / 4 非异常 / 5 已关闭 / 6 已拒绝 / 7 已终止。

## 9. 与 iOS 反推契约的差异汇总

| 项 | iOS 反推 | 后端真实 | 处理 |
|---|---|---|---|
| 响应失败文案 | `error` | `message` 面向用户、`error` 是错误码 | `failure` 优先 `message` |
| condition 值 | 中文标签 | 数字编码 / 省份 key | label→code 映射表 |
| 改密参数 | `oldPassword/newPassword` | `old_password/new_password1/new_password2` | 已修正 |
| 权限标志 | `op` | `ops`（在 `metaAuthVO` 内） | 两者兼容 |
| 详情接口 | 未明确 | `GET /<prefix>/{id}` | 已接 |
| 状态枚举 | 推测 0/2/9 | `TaskStateEnum` 1~7 | 已按枚举映射 |
| 分页 | 返回条数判断 | `additional_data.more_items_in_collection` | 已暴露 getter，列表暂用条数判断 |
| 登录密码 | — | 明文比对（无加密） | 前端不做额外处理，建议后端后续加盐哈希 |

## 13. 图片上传与新建异常（2026-11-05 实测）

### 13.1 图片上传（M0-06，D6 已定案）

**结论：走后端代传，不用 OSS STS 直传。**

原 iOS 用 `AliyunOSSUploadTool` + `GET /oss/sts` 拿临时凭证直传 OSS，Flutter 侧改为：

```
POST {baseUrl}upload/{type}/file      multipart，字段名 file
Header: token: <登录 token>
```

实测返回（本机 1601，`type=1`）：

```json
{"success":true,"data":"task/20261105/324ab9c9a99541fb87bd116e234a8f1d/16-dev-restored.png"}
```

`data` 是 **objectKey**，不是完整 URL。业务接口提交时原样传这个 key，
展示时用列表/详情接口返回的 `PictureBO.url`（服务端已拼好 OSS 域名）。

`type` 对应后端 `UploadEnum`，决定 OSS 目录前缀：

| type | 枚举 | 前缀 | 用途 |
|---|---|---|---|
| 1 | Task | `task/` | 异常照片 |
| 2 | HelpDoc | `help/` | 知识库文档 |
| 3 | Avatar | `avatar/` | 头像 |
| 4 | Ops | `ops/` | 巡检记录照片 |
| 5 | Pin | `pin/` | 讨论区帖子 |
| 6 | CheckIn | `check/` | 签到 |
| 7 | Setting | `setting/` | 设置 |
| 8 | Form | `form/` | 各类表单 |

换掉 STS 直传的三个理由：

1. 直传要引 `aliyun_oss_flutter`（原生依赖 + 凭证过期处理 + 多端配置），后端接口已做了同样的事；
2. 服务端 `UploadService.saveFile` 会顺带做 `AliyunIMM.transformOfficeDoc`（文档转码），直传会绕过；
3. 客户端不必知道 OSS 域名与 bucket，少一处硬编码。

**客户端约定**：选图时统一压到 1600px / 质量 82（`ImagePickerService`），
九张原图会到 40MB 量级，4G 下不可接受；上传时机放在提交动作里，
用户中途放弃不会在 OSS 留孤儿文件。

### 13.2 新建异常（M3-01）

**站点范围**：`POST station/datamanager`（body 可选 `startPage/limit/keyword`），
返回当前用户作为 `data_manager_id` 的站点：

```json
[{"id":209,"name":"夜郎湖","region":"贵州省","city":"安顺市","regionKey":"520000","cityKey":"520400"}]
```

这是**唯一可用范围**：`TaskCreateValidator` 硬性校验
`station.dataManagerId == task.creatorId`，否则报「该用户无权限创建该站点故障」。
换成 `station/list` 会导致提交必失败。

**提交**：`POST task/create`，body 为 `Task` 实体子集：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `content` | string | ✅ | 故障现象，空则「故障现象不能为空」 |
| `stationId` | int | ✅ | 站点 id |
| `gmt_happen` | long | ✅ | 发生时间，毫秒时间戳 |

## 15. 巡检（M4-01 ~ M4-04，2026-11-05 实测）

巡检在后端叫 **`opsrecord`**（不是 patrol/inspection），对应 `OpsController`。
契约来自 `OpsRecordService` / `OpsJobSubmitValidator` / `OpsMapper.xml`。

### 15.1 详情：`GET opsrecord/{id}`

| 字段 | 说明 |
|---|---|
| `id` / `gmt_create` / `deadline` / `gmt_first_submit` | 任务号与三个关键时间 |
| `jobNumber` | **实测为 null**（列表与详情都没返回），客户端展示「—」，不要当成必填 |
| `station` | 站点对象，含 `name` / `address` / `coordinate1` / `coordinate2` |
| `executor` / `stationManager` | `{id, nickname, avatar}` |
| `opsTaskDone` / `overtime` / `terminated` | 完成 / 过期 / 终止，展示状态按此优先级取 |
| `itemSize` | 巡检项总数 |
| `pictures` | **裸 objectKey 数组**（如 `ops/xxx.jpg`），不是 `PictureBO`，展示要自己拼 OSS 域名 |
| `opsDetailList` | 巡检项数组，见下 |
| `auth` | `{enableToSubmit, enableToTerminate, enableToTransfer, enableToForceTransfer}` |

`opsDetailList[i]`：

| 字段 | 说明 |
|---|---|
| `id` | `ops_record_detail.id`，提交时作为 `itemList[i].id` |
| `category` | 所属单元（采配水单元 / 分析单元 / 辅助设备 / 站控 / 质控 / 其他…） |

| `description` | 该项备注，未填为 null |
| `requirePhoto` | 是否必须拍照 |
| `picturesPreview` | `{picture: objectKey, url: 直链, title}` 数组 |

> ⚠️ **巡检项没有「正常 / 异常 / 不适用」状态位**。数据库 `ops_record_detail` 只有
> `pictures` 与 `description` 两列，完成度只能由「有没有备注或照片」推导。
> 规划文档里写的三态在接口里并不存在，不要凭空加字段。

### 15.2 提交前站内校验：`POST opsrecord/submit/check`

请求：`{"id": 12534276, "coordinate1": 120.16, "coordinate2": 30.37}`

判定规则在 `StationService#isCoordinateAtStation`：站点与提交点距离 **≤ 20 km** 视为站内。

| 场景 | 响应 |
|---|---|
| 站内 | `{"success": true, "data": true}` |
| 站外 | `{"success": true, "data": false, "message": "请在站房内提交巡检任务"}` |

> ⚠️ **`success` 为真不代表能提交**。必须看 `data`，只看 `success` 会把站外当成站内。

### 15.3 提交：`POST opsrecord/submit`

```json
{
  "id": 12534276,
  "itemList": [{"id": 1952594, "description": "试剂与纯水量正常", "pictures": ["ops/20261105/.../a.png"]}],
  "description": "整体备注",
  "pictures": ["ops/.../note.png"]
}
```

`OpsJobSubmitValidator` 的校验顺序（实测逐条命中）：

| 动作 | 报错 |
|---|---|
| 任务已过 `deadline` | 「任务已过期」 |
| `opsId` 不是当前用户 | 「无权限提交巡检任务」 |
| `itemList[].id` 不属于该任务 | 「运维任务项不存在」 |
| `requirePhoto` 项 `pictures` 为空 | 「<巡检项名>需要上传照片」 |
| `requirePhoto` 项少于 `photoMin` 张 | 「<巡检项名>至少上传 N 张照片」 |
| 整体 `pictures` 超过 9 张 | 「备注照片最多上传9张」 |

**实测成功用例**（任务 12534276，1 项）：提交后 `opsTaskDone=true`、
`gmt_first_submit` 写入服务端时间、`auth` 四个开关全部转 false、巡检项的
`description` 与 `pictures` 都落库（印证逐项备注是支持的，原 iOS 没做）。

`updateOpsRecordDetail` 是**整体覆盖** `pictures` / `description`，所以：
- 已填过备注的项，重新提交必须把原备注带上，否则会被清空；
- 已有照片的项，必须把原 `picturesPreview[].picture`（objectKey）一并带回，
  否则旧图会被新图替换掉。

### 15.4 终止：`POST opsrecord/{id}/terminate`

请求 `{"description": "终止原因"}`；成功后 `terminated=true`、`auth.enableToSubmit=false`。

### 15.5 评论 / 点赞

与异常、签到共用，`itemType` 必须是 **3**（`CommentTypeEnum.OpsRecord`）。

| 动作 | 接口 | 参数 |
|---|---|---|
| 读评论 | `POST comment/list` | `{itemType: 3, itemId}` |
| 发评论 | `POST comment` | `{itemType: 3, itemId, content}` |
| 读点赞 | `POST like/list` | `{itemType: 3, itemId}` |
| 点赞切换 | `POST like` | `{itemType: 3, itemId}` |

**实测**（任务 12495900）：发评论后读回 1 条；`itemType=1` 读同一条返回 `[]`；
点赞连点两次 1 → 0。

### 15.6 客户端落地

- 详情 `InspectionDetailPage`：站点/状态/编号/项目数/处理人/时间 + 按单元分组的

## 16. 消息（M6-01 / M6-02，2026-11-05 实测）

契约来自 `ops-mobile` 的 `MessageController` / `MessageService` / `PushMessageEnum`，
安卓侧的参照实现是 `MessageFragment` + `ExceptionTaskPresenter`（`message/list`、`message/type`）。

**消息不是聊天**：服务端是「推送流水」，一条消息对应一条业务事件，没有会话、没有发送接口。
原规划里的「聊天详情 / 发图片 / 发送重试」在接口层面不存在，实现按流水做。

### 16.1 分类列表：`POST message/list`（无请求体）

`data` 固定 7 条，顺序由 `PushMessageEnum` 决定：

```json
[
  {"messageType": 1, "messageName": "异常任务", "latest_message_title": "测试-老虎潭水库-新任务",
   "latest_message_time": "2026-11-05 09:46", "unread_count": 1},
  {"messageType": 4, "messageName": "收到评论", "latest_message_title": "【巡检任务】卜幸杰评论了你",
   "latest_message_time": "2026-11-05 13:20", "unread_count": 2}
]
```

| 编码 | 分类 | 备注 |
|---|---|---|
| 1 | 异常任务 | 点进去可跳 `/task/{jobId}` |
| 2 | 巡检任务 | 点进去可跳 `/inspection/{jobId}` |
| 3 | 转交任务 | 额外有同意 / 拒绝 |
| 4 | 收到评论 | 无独立详情页 |
| 5 | 收到的赞 | 无独立详情页 |
| 6 | 我的申请 | `jobType=5`，属 `apply` 模块，客户端未接 |
| 7 | 我的审批 | `jobType=6`，同上 |

没有消息的分类同样下发，`latest_message_title` 为「暂无消息」、`unread_count` 为 0。

### 16.2 分类明细：`POST message/type`

```json
{"type": 1, "startPage": 1, "limit": 20}
```

`data` 为消息数组，`additional_data` 为分页对象（`total` / `totalPage` / `more_items_in_collection`）。

单条字段：

| 字段 | 说明 |
|---|---|
| `id` | 消息 id，转交处置时要用 |
| `message_type` | 分类编码，**下划线**命名（与 `message/list` 的 `messageType` 不同！） |
| `title` / `content` | 标题 + 正文；`content` 可能是评论内容，转交处置后变成「已同意」「已拒绝」 |
| `description_left` / `description_right` | 已带前缀，如「来源:卜幸杰」「截止时间:2026-11-05 17:46」 |
| `gmt_create` | 形如 `2026-11-05T09:46:39.000+0800` |
| `jobType` | 1 异常 / 2 巡检 / 5 申请 / 6 审批 |
| `jobId` | 对应业务主键，跳详情用 |
| `accepted` | **仅转交类有效**：`null` 待处理，`true`/`false` 已同意/已拒绝 |

> ⚠️ **取一次列表 = 该分类全部已读**。服务端先执行
> `UPDATE push_message SET is_read=1 WHERE message_type=? AND user_id=?`，再查数据。
> 所以「点开分类」这个动作本身就会把未读清零，客户端必须同步刷新角标
> （否则用户返回后仍看到红点，但点进去又没有未读）。

### 16.3 转交处置：`POST message/transfer`

```json
{"id": 40704, "accepted": true}
```

`MessageTransferValidator` 的校验顺序（实测逐条命中）：

| 场景 | 报错 |
|---|---|
| 缺 `accepted` | 「请选择同意或拒绝」 |
| 消息已处置（`accepted` 非空） | 「消息无法变更状态」 |
| 不是自己的消息 | 「你无权限确认转交请求」 |
| 业务层（`TaskTransferAcceptValidator` / `OpsTransferAcceptValidator`）不通过 | 由对应校验器给文案 |

成功后：消息 `content` 写入「已同意」/「已拒绝」、`accepted` 落库，
并同步业务表（`taskService.acceptTransferTask` / `opsService.acceptTransferTask`），**不可撤销**。
接口不返回新消息体，客户端需自行刷新。

### 16.4 未读总数：`POST message/count_unread`

返回 `data` 为整数。`message/list` 的 `unread_count` 求和与之相等。

### 16.5 客户端落地

- `MessagePage`：7 个分类固定展示 + 未读汇总卡；下拉刷新；
  无「全部已读」接口，按钮实现为**对有未读的分类逐个 `message/type {limit:1}`**（最多 7 次轻请求），
  先本地清零给即时反馈，结束再 `refresh()` 校准。
- `MessageListPage`（`/message/:code`）：分页（触底加载）、下拉刷新、点卡片按 `jobType` 跳详情；
  申请 / 审批无详情页，给「请到 XX 查看」提示而不是白屏。
- 进列表后调 `refreshMessageUnread`，把分类角标与底部导航角标一起刷新。

## 17. 推送（M6-04，2026-11-05 端到端验证）

### 17.1 客户端要什么

**客户端只需要 AppID**。AppKey / AppSecret / MasterSecret 只在服务端推消息时使用。

| 项 | 值 | 位置 |
|---|---|---|
| AppID | `xD7UWWJDKl8jmq6AiuNnC2` | `android/app/build.gradle.kts` 的 `manifestPlaceholders["GETUI_APPID"]` |
| SDK | `com.getui:gtsdk:3.3.12.0` + `com.getui:gtc:3.2.18.0` | `android/app/build.gradle.kts` 的 dependencies |
| Maven | `https://mvn.getui.com/nexus/content/repositories/releases/` | 根 `build.gradle.kts` |

AppKey / AppSecret / MasterSecret 见后端 `application.properties` 的 `gpush.*`（不入客户端）。

### 17.2 为什么没用官方 getuiflut 插件

`getuiflut` 0.2.41 的 Android 工程仍是 AGP 4.2 写法：
`compileSdkVersion`（AGP 9 已移除）、`jcenter()`（已停服）、`lintOptions`（已改名）。
本项目是 **AGP 9.1 + Gradle 9.3.1**，直接依赖必然编译失败。

改为**直接依赖个推 AAR + 自建 MethodChannel**，只暴露五个能力：

| 通道方法 | 作用 |
|---|---|
| `init` | 初始化 SDK，返回当前 CID（可能为空，异步下发） |
| `bindAlias {alias}` | 绑别名 |
| `unbindAlias {alias}` | 解绑别名 |
| `getClientId` | 取当前 CID |
| `isNotificationPermissionGranted` / `requestNotificationPermission` | Android 13+ 通知权限 |

原生文件：`android/app/src/main/kotlin/.../push/{PushBridge,GreenPushService,GreenIntentService}.kt`，
清单里两个 service 必须注册（`GreenPushService` 要跑在 `:pushservice` 独立进程，否则长连接不建立）。

### 17.3 别名规则（关键）

服务端 `AppPushService.PREFIX = "LJYW"`，发送时 `alias = "LJYW" + userId`。

客户端登录后必须绑 **同一个** 别名：`LJYW16`（userId=16）。

> ⚠️ 原 Android 工程有 bug：`MyApplication.onCreate` 冷启动时绑的是 `userId`（**无前缀**），
> 登录页又绑 `"LJYW" + id`（有前缀）。后端统一加前缀推送，所以冷启动那条绑定永远收不到。
> Flutter 版统一 `LJYW + userId`，见 `pushAliasFor()`。

### 17.4 服务端推送协议（个推 v2 REST，实测可用）

```
POST https://restapi.getui.com/v2/{appId}/auth
  {sign: sha256(appKey + timestamp + masterSecret), timestamp, appkey}  → token

POST https://restapi.getui.com/v2/{appId}/push/single/alias
  Headers: token
  {request_id, audience:{alias:["LJYW16"]}, settings:{ttl},
   push_message:{notification:{title, body, click_type:"startapp"}}}
```

返回 `data.<taskId>.<cid> = "successed_online"` 表示在线通道投递成功。

> ⚠️ 个推对消息文案有**敏感词过滤**，含「个推」二字会返回
> `code 20001: param contains sensitive word`。

## 18. 委派任务 / 转交（C7，2026-11-05 实测）

异常详情「更多」面板 → 转交任务。发起转交两条接口：候选处理人 + 转交动作。

### 18.1 候选处理人：`POST user/ops/list`

body `{"keyword": "bxj"}`（可选；不传分页时返回全量，与原工程一致）。

- 服务端 SQL：`is_ops = 1 and is_active = 1`（在职运维），按昵称 / 全拼 / 简拼
  like 匹配，**大小写不敏感**，`order by firstchar`。
- `data[]` 是完整 User 序列化（大量 null 字段），有效列为
  `id, nickname, pinyin（实测全大写，如 BUXINGJIE）, jianpin, firstchar`。
- `additional_data` = 命中总数。
- 实测：`keyword=bxj` / `BXJ` 均返回 1 条（卜幸杰）。

### 18.2 发起转交：`POST task/transfer`

body 对齐 `JobTransferLog`：

| 字段 | 说明 |
|---|---|
| `jobId` | 任务 id（故障，`jobType` 不传） |
| `toUserId` | 接收人 id |
| `force` | 默认 false；true 为站点管理员强转（直接生效，`enableToForceTransfer`） |
| `fromUserId` | **不要传**，服务端从 token 解出 |

服务端校验（`TaskTransferValidator`）：

1. 任务存在且状态 = 待处理（1）；
2. `transferToUserId == null`（只能转交一次，管理员强转除外）；
3. 不能转给自己；
4. 接收人必须在职且是运维（`active && ops`）。

服务端副作用（`TaskService#transferTask`）：写任务日志「转交任务给X，待接受」、
给接收人插 `Transfer` 类型消息（16.3 的 `message/transfer` 就是处置它）、个推推送。
非强转时**接收人接受前任务处于转交冻结**：`enableToSubmit` 变 false，双方都不能处理。
